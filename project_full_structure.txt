========================
1) PROJECT OVERVIEW
========================
- ระบบ: ERP สำหรับอพาร์ตเมนต์/คอนโดหนึ่งอาคาร ครอบคลุมบิลรายเดือน, ชำระเงิน, เอกสาร, เทมเพลต, ตั๋วแจ้งงาน, กล่องข้อความ และอินทิเกรชัน LINE ขั้นต้น
- สถาปัตยกรรม:
  - Frontend: Next.js 14 App Router (React 18), client/server components
  - Backend: Next.js route handlers (app/api/*) ทำงานบน Node runtime, service layer แยกใน src/services/*
  - Database: PostgreSQL ผ่าน Prisma ORM
  - External services: ไม่มีภายนอกบังคับ ใช้ LINE เฉพาะการ bind/approve (ยังไม่มี webhook)
  - Operational layer: backup/restore scripts, health monitor, error monitor, file logger พร้อม rotation
- เทคโนโลยีหลัก:
  - Framework: Next.js 14.2.x, React 18.3.x
  - Language: TypeScript (strict)
  - ORM: Prisma 5.22.0
  - DB: PostgreSQL
  - Logging: ไฟล์ logs/app.log (หมุนไฟล์ >10MB)
  - Rate limit: in-memory per IP+route
  - Idempotency: in-memory guard สำหรับ critical ops
- Environment config สำคัญ:
  - DATABASE_URL: เชื่อมต่อ Postgres
  - BACKUP_DIR: โฟลเดอร์เก็บไฟล์ backup (default ./backups)
  - LOG_DIR: โฟลเดอร์ log (default ./logs)
  - APP_VERSION: เวอร์ชันที่รายงานใน /api/health
  - HEALTH_URL: สำหรับ scripts/monitor.ts (optional)

4) DATABASE ANALYSIS
========================
- Prisma schema (ตัดวางทั้งหมด):
------------------------------------------------------------
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

[...] (ดูไฟล์ prisma/schema.prisma ใน repo; ประกอบด้วย: Tenant, User, Role, Permission, UserRole, Floor, Room, Resident, LineBinding, Contract, MoveHistory, BillingMonth, BillingRecord, DocumentTemplate, DocumentVersion, DocumentSendLog, Payment, PaymentMatch, Ticket, TicketMessage, LineMessage, RoomResident, Conversation, ConversationMessage, BillingFieldMapping, AuditLog; enums RoomStatus, RoomType, TicketStatus, DocumentStatus, BillingStatus, MessageSender)
------------------------------------------------------------
- Primary Key: ทุก model มี id/string cuid() หรือ natural key (Room.number)
- Foreign keys: ความสัมพันธ์ระบุใน schema (Room→Floor, BillingRecord→Room/BillingMonth, DocumentVersion→Template/Room/BillingMonth, PaymentMatch→Payment/BillingRecord ฯลฯ)
- Index:
  - Unique: BillingMonth(year,month), BillingRecord(roomNumber,billingMonthId), DocumentVersion(templateId,roomNumber,billingMonthId,versionNo)
  - Index ทั่วไป: RoomResident(roomNumber), RoomResident(residentId), Conversation(roomNumber), Conversation(residentId)
- Soft delete: ไม่มี (ใช้ delete/update ปกติ)
- Audit fields: createdAt หลายตาราง, updatedAt ใน BillingRecord, AuditLog เก็บเหตุการณ์
- Snapshot table: ไม่มีตาราง snapshot แยก
- Billing lock: BillingMonth.closed (boolean) ใช้เป็น lock

5) BUSINESS LOGIC DEPTH CHECK
========================
- billing snapshot: ยัง (ไม่มี snapshot แยก)
- monthly lock: มี (BillingMonth.closed + ตรวจใน service)
- regenerate confirmation check: มี (ถ้า SENT แล้วต้อง force; ปัจจุบันบังคับผ่าน ConflictError และ force flag ใน generate route)
- billing change detection: มีระดับ optimistic locking ใน BillingRecord.updatedAt
- payment overpay handling: มี guard ไม่ให้เกินยอดใบแจ้งหนี้หรือยอดชำระเงิน
- payment partial handling: รองรับ partial ผ่าน PaymentMatch หลายรายการ
- room status timeline: มี MoveHistory/RoomResident แต่ยังไม่มี full logic บันทึกทุกเหตุการณ์
- resident history timeline: โครงสร้างพร้อม (RoomResident, MoveHistory) แต่ logic ยังบาง
- document version reset per month: ใช้ count ต่อ (template, room, billingMonth) เริ่มจาก 1 ในแต่ละเดือน
- LINE send logging per version: มี DocumentSendLog + AuditLog เมื่อส่ง

========================
6) SECURITY CHECK
========================
- Authentication: ไม่มีระบบ login จริง ใช้ x-admin-id/x-admin-role headers ใน production (requireAdmin)
- JWT/session: ไม่มี
- RBAC: มีใน service layer (requireRole) และ docs role matrix
- Rate limit: มีในทุก API ผ่าน in-memory limiter
- Input validation: ใช้ zod ใน POST/PATCH ที่สำคัญ
- Encryption for PII: ไม่มีการเข้ารหัสข้อมูลส่วนบุคคลใน DB
- LINE webhook signature verify: ไม่มี webhook endpoint

========================
8) CRITICAL MISSING PARTS
========================
- ขาดแล้วเสี่ยง:
  - ระบบ Authentication/Session จริง + CSRF protection
  - LINE webhook + signature verification
  - PII encryption at rest/in transit beyond TLS (เช่น hashing หรือ field-level encryption)
  - Backup encryption + offsite retention และ restore drill automation
  - Snapshot/immutable history สำหรับ Billing/Payments เพื่อ audit เชิงบัญชี
- ควรทำก่อน production:
  - เพิ่ม real auth (NextAuth/JWT/session) + enforce RBAC ที่ API ชั้นนอกทุกตัว
  - เพิ่ม webhook handler สำหรับ LINE + verify HMAC
  - เพิ่ม billing snapshots และ soft-delete/archival strategy
  - เพิ่ม structured error codes บน API responses ให้สม่ำเสมอ
  - เพิ่ม e2e tests สำหรับ flows วิจารณ์สูง (close month, match payment, generate/send docs)
- Nice-to-have:
  - ระบบ notification queue (email/LINE) สำหรับส่งเอกสาร/แจ้งเตือน
  - Dashboard realtime และ metrics
  - Background job worker สำหรับงานหนัก (PDF/Docx batch)
  - Configurable rate limit per role/route

หมายเหตุปฏิบัติการ:
- /api/health รายงาน backup freshness และ log size; scripts/monitor.ts ใช้คุมครอน
- File logger หมุนไฟล์ >10MB; สถานะ degraded หาก log dir >200MB
- Scripts backup/restore พร้อม และ tests/build/typecheck ผ่าน
